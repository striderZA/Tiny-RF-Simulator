# app/AGENTS.md

## Purpose
Application composition and UI orchestration: the UI-free `simulator::circuit_runtime` and `simulator::editor_services` targets, plus `CircuitRuntime`, `GraphEditorActions`, `RfSimulatorApp`, `ComponentTypeRegistry`, `InspectorPanel`, `PFBViewManager`, instrument widgets, project serializer, and component-library UI.

## Ownership
- `RfSimulatorApp` — application boot, frame loop, DSP update, and UI orchestration; declares `CircuitRuntime` before every dependent widget/controller so its live model outlasts them (project save/load logic lives in `ProjectSerializer`)
- `CircuitRuntime` — UI-independent owner of the live graph, view manager, component registry, component IDs, validated topology commands, synchronous rewiring, and topological DSP update; `simulator::circuit_runtime` has no UI dependency
- `simulator::editor_services` — static UI-free boundary for `EditorCommands`, `GraphEditorActions`, `ComponentTypeRegistry`, `ComponentLibrary`, receiver-requirements validation/evaluation, and `ReceiverPerformanceMeasurementEngine`; publishes `app/include` and runtime/engine dependencies without UI include paths
- `GraphEditorActions` — low-level app adapter for probe/group/selection/part-number mutations and group-boundary rebuilding; user-level edits reach it through `EditorCommands`, while `ProjectSerializer` uses it directly for bulk restoration
- `EditorCommands` — UI-free single entry point for user-level project edits (component create/remove/adopt, link connect/disconnect, probe add/remove, group create/rename/collapse/remove, group selection); each command applies its side effects in one place (group-boundary rebuild, `onComponentsChanged` view sync, revision advance; probe edits deliberately do not advance the revision) and owns the derived dirty state (`revision()`, `markModified()`, `markClean()`, `isDirty()`)
- `ComponentRegistry` — runtime-owned component collection and type-indexed lookup; its implementation is part of `simulator::circuit_runtime`
- `InspectorPanel` — property editing panel; parameter edits report through `onParamChange`, and group rename/ungroup/selection go through `EditorCommands`
- `ComponentTypeRegistry` — the 13-row dispatch table for canvas menu, add, duplicate, save/load, inspector drawing, and component authoring; each row carries its canonical types, factory, inspector, authoring `fields`, and `state_fields` for every scalar leaf of the engine's `serialize()` snapshot
- `PFBViewManager` — owns the per-PFB IQ Plot / Channelizer Grid widgets and their visibility. `sync()` derives them from the registry's PFBs in registry order: surviving PFBs keep their widgets and in-session visibility, new PFBs load persisted visibility, and removed PFBs' views are destroyed. `clear()` is reserved for bulk engine destruction and runs first in `ProjectSerializer::reset()`, before the engines are destroyed; views are keyed by graph node id, which is reset only after that clear. No add/duplicate/load/remove path branches on the PFB type; issue #37's lockstep-vector use-after-free stays closed because every component-set change syncs before views draw again
- `NetworkAnalyzerEngine` / `NetworkAnalyzerWidget` — singleton instrument panel owned by `RfSimulatorApp`; the engine reads the runtime's const graph and `NaHost` resolves engines through its const component view, while each measurement uses a private scratch graph/registry. The reusable `MeasurementChainPath` / `IsolatedChainRunner` stay in `network_analyzer_engine` (common + node_graph_engine only); app-owned `NaScratch` clones through `ComponentTypeRegistry` into that private graph/registry
- `PowerMeterEngine` / `PowerMeterWidget` — singleton observer instrument owned directly by `RfSimulatorApp`; the UI widget selects a live graph output pin while the UI-independent engine measures total instantaneous power in dBm; it is not an `IComponentEngine`, registry row, graph node, or project-state source selection
- `ReceiverPerformanceMeasurementEngine` — UI-free cached output-power/IIP3 measurements over the shared `MeasurementChainPath` / `IsolatedChainRunner`; it uses isolated scratch clones and the selected Point A generator reference tone for output power, combining coincident output tones as phase-aware RMS-voltage phasors. The synthetic output-tone sweep runs only when output power is enabled; IIP3 tone matching uses a tolerance below its configured separation and rejects unrepresentable fundamentals/products. Every IIP3 fundamental and IM3 frequency must remain within the inclusive `MIN_FREQ..MAX_FREQ` bounds. IIP3 fits collect finite observations independently for each fundamental/IM3 side and require at least three valid points plus credible fit quality on all four lines. `update()` spends at most 4 ms on scratch stimuli per call and resumes pending sweeps; an optional `setMaxRunsPerUpdate()` cap also bounds the chain runs per call (the app never sets it; tests do, so progress per call does not depend on build speed). No worker threads or widget/graph traversal.
- `PfbCalculatorWidget` — dockable PFB filter calculator owned directly by `RfSimulatorApp` (`m_calculator_widget`): binds M/K/beta + rejection target to the graph-selected (or combo-picked) PFB and applies them through the engine's setters; all response math comes from `PfbFilterDesign` in `pfb_channelizer/` so tool and engine can never drift
- `TestFlowWidget` — app-owned Test Flow runner panel (`m_test_flow_widget`), constructed with const runtime graph/registry views and never an `RfSimulatorApp` reference; it validates and runs through the GUI-free `test_flow` harness, while native dialogs remain app-owned
- `ReceiverRequirementsWidget` — app-owned dockable editor; stages the required band and independently enabled gain, noise-figure, output-power, and IIP3 limits/conditions. It renders source-tone choices, results, statuses, and validation feedback but never traverses the graph or measures. Apply validates and commits the entire draft while keeping the view open; Cancel restores the applied snapshot. It auto-preselects only a sole finite positive source tone and updates the draft baseline without hiding applied results; the reference tone is committed only when output-power measurement is enabled.
- `ProjectSerializer` — app-bound `.rfsim` save/load/reset orchestration; reads const runtime views and routes live component/link operations through `CircuitRuntime` and editor-state restoration through `GraphEditorActions`. Bulk restoration deliberately bypasses `EditorCommands` (no revision change), and it creates no component-bound views: `RfSimulatorApp` re-syncs them after every `load()` and `reset()`
- `RfSimulatorApp` owns `ReceiverRequirementsState` as project data before `m_serializer` in declaration order, so the referenced state outlives `ProjectSerializer`; it is not session/global state. It constructs `ReceiverPerformanceMeasurementEngine` after `NaHost`, which outlives the engine's host reference.
- `ComponentFormModel` / `ComponentFormWidget` — pure-logic + ImGui rendering pair for the New/Edit Component form
- `ExtensionManager` — extension manifest discovery and status tracking across built-in/global/project-local roots, plus the project-local provenance query the trust gate reads
- `ExtensionTrustStore` — exe-relative (`<exe_dir>/extension_trust.json`) record of the extension directories the user allowed to execute, keyed by canonical extension root
- `ExternalToolRunner` — structured request/result execution for approved external tools
- `library_package` — `.rflib` ZIP export/import: exports loader-valid component definitions and only their referenced assets; imports validate the whole package before writes, skip/report conflicts by component identity, and stage accepted entries before installing under the global user library root

## Local Contracts
- `RfSimulatorApp::saveProject()` / `loadProject()` / `newProject()` are thin wrappers that delegate to `ProjectSerializer::save()` / `load()` / `reset()`; all `.rfsim` JSON serialization lives in `ProjectSerializer`
- `ParameterField::key` in `fields` names component-library authoring parameters; `state_fields` instead describes every engine `serialize()` scalar leaf under its persisted key. It carries kind, unit, enum labels, help, and writability, but leaves `min`/`max` unset because ImGui call sites own edit limits; only `sparam_filepath` is read-only, and the authoring form ignores that flag. `normalizeStatePath()` maps indexed array paths such as `tones[12].freq_Hz` to `tones[].freq_Hz`, and `findStateField()` accepts either form. `.rfsim` parameters and Test Flow conditions still use each engine's actual serialization keys and encodings; do not rename or re-encode a persisted key without an explicit versioned migration. Issue #174 and `test_component_params` pin these contracts.
- Receiver requirements are optional project data in the top-level `receiver_requirements` object. Missing data in legacy files means Not configured; malformed objects/fields/limits are retained as Invalid configuration with a diagnostic and do not abort other project restoration. If initial JSON parsing fails, overflow recovery isolates this top-level value and replaces only its overflowing numeric tokens with `null` outside quoted strings before typed validation; it handles leading UTF-8 BOMs accepted by the JSON parser, while overflow elsewhere remains a load failure rather than silently changing unrelated data. Other malformed whole-file JSON remains a load failure, and the 64 MiB file cap applies before parsing. Any supplied measurement condition must be valid even when its metric is disabled; enabled IIP3 sweeps require 3–101 distinct advancing levels. Saving invalid state writes an explicit invalid marker and diagnostic; `newProject()` clears configured and invalid requirements, including optional measurement conditions.
- `ProjectSerializer::load()` validates top-level `.rfsim` shapes (arrays for `components`/`links`/`probe_pins`/`groups`, objects for `network_analyzer`/`window_state`/`graph_state`) and isolates malformed records: a wrong top-level shape aborts the load with a logged error (state reset to empty), while malformed component/graph entries are logged and skipped so valid siblings still restore; JSON and non-JSON exceptions are caught and surfaced as a logged `false` result, never thrown to the caller. `lastLoadReset()` distinguishes failed loads that reset state from failures that leave the current project intact. When it is true, `RfSimulatorApp::loadProject()` clears `m_current_project_path`, marks the project dirty, and calls `refreshExtensions()` so project-local extension discovery re-roots at the CWD instead of leaving the destroyed project's tools/data packs active, so a failed load that already destroyed the live project can never leave the previous file as the Ctrl+S save target (issue #113). The destroyed circuit is also a Test Flow circuit reload, so the same branch resets the panel (see the latch contract below). Field-level shape validation for the two singleton sections runs before any reset, driven by the single `windowFlags()` list that also feeds `save()` and the restore (so a new flag cannot be persisted without being shape-validated): a non-boolean `window_state` flag or a fractional/negative/over-`int` `graph_state.next_component_id` is logged and the load is rejected with the live project and its current save path left completely untouched — deliberately distinct from a wrong-shaped top-level section, which resets and aborts (issue #113).
- `ProjectSerializer::save()` is atomic (issue #113): it serializes to a sibling `<path>.tmp`, checks the stream after write/flush/close, and only then `std::filesystem::rename`s it over the target — `rename` replaces an existing file on every supported platform, so there is deliberately no remove+rename fallback (deleting the target first would reintroduce the data-loss window). A temp open/write/flush/close failure or a failed rename returns `false` (logged), removes the temp file, and leaves the original byte-identical. `RfSimulatorApp::saveProject()` adopts the path and clears dirty state only on success, so a failed save leaves the project dirty on its previous path and the unsaved-changes modal stays open for a retry (issue #77).
- Dirty state is derived: `RfSimulatorApp::isDirty()` is `EditorCommands::isDirty()`, i.e. the project revision differs from the one recorded by the last successful save, successful load, or New (`markClean()`). Accepted `EditorCommands` edits advance the revision themselves (rejected ones never do); edits outside the command service — inspector parameters (`onParamChange`), node moves, Network Analyzer / Receiver Requirements / calculator state, component-form saves — call `markDirty()`, which is `markModified()`. Spectrum probe add/remove and group selection do not advance the revision (probe edits keep their pre-`EditorCommands` semantics even though `.rfsim` saves `probe_pins`; changing that is a separate decision). `projectRevision()` lets tests prove an operation recorded no edit even from an already-dirty baseline.
- The app's `test*` topology/probe/group commands forward to the same `EditorCommands` calls as the editor widget, so fixtures built through them carry the editor's side effects, including the revision; `testCreateComponent()` additionally pins the caller's engine id and restores the runtime's id counter.
- File menu bar in `draw_ui()` handles keyboard shortcuts (`Ctrl+N`, `Ctrl+O`, `Ctrl+S`, `Ctrl+Shift+S`) and unsaved-changes modal; Help menu provides the F1-toggled help window and `Help > Tutorial`
- `Help > Tutorial` and the first-run "Welcome" modal both route through `requestTutorial()`, which runs the same `PendingAction`/unsaved-changes guard as New/Open/Exit (`PendingAction::Tutorial`) before `startTutorial()` resets to a seeded sandbox. Any new `PendingAction` value must be handled in both the Save and Discard branches of that modal.
- The first-run offer is driven by `m_show_tutorial_first_run_prompt`, set on construction from `TutorialState::completed()` (see `tutorial/AGENTS.md`); either answer marks it completed so the prompt never repeats
- View menu's `Layouts` submenu (Save As.../Load/Manage...) drives `LayoutManager` (see `layout/AGENTS.md`) for named window-layout presets; the exe-relative default layout is auto-managed by ImGui itself via `IniFilename`, set in `core/src/core.cpp`
- Library browser's "New Component..."/"Edit" flow writes schema-v2 JSON via `ComponentFormModel::buildDefinition()`; new entries save to a user-chosen root (`rf-sim-libraries/` project-local or `~/.rf-sim/libraries/` global); built-in `component_data/library/` entries are read-only (no Edit button) and never a save target; clicking Edit on a user entry opens the form without inserting it; edits always overwrite the original `source_path` (no rename-on-identity-change)
- Authoring file names are traversal-proof (issue #120): the JSON/directory names and the name of the S-param file copied beside them all come from `sanitizePathSegment()` (declared in `component_library.h`, shared with `app.cpp`), and the copy destination is built with `dataFileCopyDestination(dest_dir, name)`, which returns nullopt for anything that is not a bare file name (separator, drive/root prefix, `.`/`..`, empty) — `saveComponentForm()` then refuses the save with an error instead of joining an escaping name. `ComponentLibrary`'s own `data_file` resolution (`resolveDataFilePath`) stays the looser containment rule for reads, since a library entry may legitimately reference a file in a subdirectory. That gate cannot fire through `buildDefinition()` — the model's name is always safe — and is kept as defence in depth, with its rejection table unit-tested against `dataFileCopyDestination()`. The save path itself is covered end to end (new entry and edit) by `tests/test_path_containment.cpp` through the form's test accessors (`testOpenNewComponentForm(type, root)`, `testOpenEditComponentForm(def)`, `testSetComponentFormDestinationRoot(root)`, `testComponentFormModel()`, `testSaveComponentForm()`), which stand in for the modal's Project/Global buttons and the native S-param picker.
- Extension discovery stays inside `app/` and scans built-in, global, and project-local roots; invalid manifests remain visible via `ExtensionManager::all()`
- Extension ids are first-root-wins in `scanRoots()` order (source-tree built-in > exe-dir built-in > global > project-local), regardless of the incumbent's status: a later manifest reusing a known id is never a replacement (even when the winning manifest is `Invalid`/`Incompatible`, which is a tested policy pin), it is kept as an `ExtensionStatusKind::Shadowed` record with `shadow_detail` naming the winning manifest and a `LOG_WARN`, and is excluded from `dataPacks()`/`externalTools()` because both filter on `status == Ok` (issue #45; the earlier last-root-wins override is now a tested rejection)
- `ExtensionManager::projectExtensionRoot()` reports the canonical `<project_root>/rf-sim-extensions` captured by the last `rescan()`; it is empty only when that path itself is unresolvable, and an empty `project_root` resolves under the CWD exactly like `refreshExtensions()` treats "no project open" (stricter gating, never looser). `isProjectLocal()` answers true on either of two grounds: the manifest's canonical `root_dir` is contained in that root, or the record was discovered through the project-root scan slot (`scanRoots()` returns provenance-tagged `ScanRoot` entries, and the slot's manifests land in the `m_project_local_roots` stamp) — the stamp is what closes the symlink hole, because a linked extension resolves outside the canonical root yet the project shipping the link ships the trigger; provenance needs no per-record root enum
- Project-local `external-tool` records are the only gated ones: `extensionRequiresTrust()` is true exactly when a manifest's `kind` is `external-tool` *and* it is project-local *and* `ExtensionTrustStore::isApproved(root_dir)` is false, so built-in/global extensions and project-local data packs are unaffected. `toolsMenuEntries()` is the single owner of that decision for the `Tools` menu, so an untrusted tool is absent from it entirely (its label is manifest-controlled); the panel shows a `Trust...` button instead of Run buttons, and `runExternalTool()` refuses it before creating any workspace (issue #45)
- Granting trust and running are separate user actions: the `Untrusted Extension` modal (last call in `draw_ui()`, driven by `m_show_extension_trust_prompt` + `m_pending_trust_manifest`) only writes the approval, and the user launches the tool afterwards; `denyPendingExtensionTrust()` records nothing, so default-deny needs no persisted denials
- `ExtensionTrustStore` fails closed: missing/invalid/unknown-`schema_version` files (compared at `int64` width so a value that narrows onto 1, e.g. 4294967297, cannot masquerade as v1) and malformed entries yield no approval (valid siblings survive, each case logged); a row is filed under `fs::weakly_canonical()` of its `root` on both sides (so a hand-edited spelling stays findable and revocable) and `approve()` refuses a manifest with an empty `id`/`version`/`entry_path`; a failed write returns `false` so `approve()`/`revoke()` resync memory from the file and the app reports `storePath()`; approvals deliberately do not re-prompt on edits, and the panel surfaces any stored approval whose `id`, `version`, or `entry_path` differs from the live manifest so revocation is the review point
- App-level tests use the public `m_extension_trust` and must `setStorePath()` to a unique temp file before approving or running a project-local tool, otherwise they write into the developer's real `<exe_dir>/extension_trust.json` (and reused temp fixture dirs would leak approvals between tests)
- `ComponentLibrary::loadFile()` / `scan()` continue discovery across malformed files: definitions with valid required fields (`type`, `part_number`, `parameters`) and type-registry-valid parameters are retained, with malformed optional metadata defaulted (a present-but-malformed `schema_version` is logged and defaulted to 1; non-string `manufacturer`/`description`/`notes` are silently defaulted); definitions with missing or wrong-typed required fields or invalid type-registry parameters are logged and dropped; malformed `data_files` children are logged and skipped individually so valid siblings are kept; filesystem errors are logged without aborting later siblings, and no JSON or filesystem exception propagates out of the library layer
- `ComponentLibrary` never stores or instantiates definitions that fail type-registry validation (issue #79): `loadFile()`/`scan()` log and drop definitions whose parameters are wrong-typed, out of range, or have an invalid enum/unknown `type`; `upsert()` refuses issue-ful definitions; `instantiate()` refuses them too and wraps engine `deserialize()` in a rollback boundary — a definition that passes field validation but still makes `deserialize()` throw (engine-state keys the library schema does not describe) is logged, the just-created node is removed from registry/graph, and `nullptr` is returned, never an exception or a partially registered component. Path-bearing parameters (`sparam_filepath`/`sparam_path`) in a definition are resolved against the library JSON's directory with the same containment discipline as `data_files` entries
- `ComponentTypeDescriptor::supports_sparam_file` drives the New/Edit picker; `load_sparam_file` dispatches the contained `data_files` asset to the matching engine. `SParameterData` accepts only Touchstone S-parameter matrices. Transfer engines require at least two ports, the combiner exactly three; mode setters still allow enabling the picker before a file is chosen but reject incompatible loaded data. Unsupported, unsafe, incompatible, unloadable, and extra references are logged. Project-file S-param paths remain subject to project-directory containment.
- Component authoring refuses symlink S-parameter destinations and existing files unless the edited definition already references that local asset and no other loaded definition references it; new entries never overwrite existing assets. Picked assets and component JSON are staged before commit; if definition replacement fails, the asset update is rolled back, and any rollback failure is shown in the form error.
- An ideal filter definition must carry the cutoffs its `filter_type` uses (issue #181), because `IdealFilterEngine::deserialize()` silently keeps its constructor defaults for a missing one: `ComponentLibrary::validate()` requires `fc_low_Hz` for LPF/HPF, and both cutoffs with `fc_low_Hz < fc_high_Hz` for BPF/BSF. An LPF/HPF `fc_high_Hz` is not checked, since the engine ignores it. The rule lives in `validate()` itself, so `loadFile()`, `upsert()`, `instantiate()`, and the form all enforce it. The authoring form shows the same per-type view through `ComponentFormModel::fieldLabel()`: a single "Cutoff" (`fc_low_Hz`) for LPF/HPF, "Low Cutoff"/"High Cutoff" for BPF/BSF, and neither until a type is chosen. Hiding is presentation only: a hidden cutoff keeps its value in the saved definition and is still validated. `ComponentFormWidget` renders a shown field's first issue beneath it and lists whole-definition issues and those of a hidden field under Save, so Save is never disabled without a visible reason; a shown field's further issues appear only in the issue count beside Save.
- External tools run only through `ExternalToolRunner` on explicit user action, and only after the app's trust gate has cleared the manifest; each `run()` executes in a fresh unique workspace under the requested temp root, writes a JSON request file, waits for the tool, and treats a missing, oversized (over 1 MiB), or invalid result file as failure; timed-out runs terminate the tool's whole descendant tree
- `runExternalTool()` refuses an untrusted project-local manifest first (see the trust gate above), then serializes the clicked action label as `action_label`, runs only under the canonical `temp/rf-sim-extension-run` root (extension `id`s are allowlist-validated at parse; canonical containment is re-checked before launch), refreshes discovery after a successful run, and updates `m_extension_result_message`
- `externalToolActions()` is the single policy for launchable tool actions: declared `menus[]` entries pass through unchanged; tools with no menus get one synthetic `"tools"` action using `manifest.name`. Because a label is the action's only identifier at run time (`action_label`) and the menu item is keyed on it, `parseMenus()` rejects a manifest declaring two entries with the same `(location, label)` pair — the same fatal treatment as every other manifest validation failure, rather than keeping an entry that cannot be addressed (issue #130)
- `refreshExtensions()` rescans built-in, global, and project-local roots for the current project path and rebuilds the component library before the browser/UI reads from it
- `.rflib` packages contain a versioned `rf-sim-library-package` manifest and component JSON plus only referenced `data_files`, `sparam_filepath`, and `sparam_path` assets; import validates every manifest, definition, asset reference, path, and archive limit before writing anything. Malformed packages are refused with no writes. Component identity conflicts already present in the global library root are skipped and reported individually; non-conflicting entries install as a staged set under `<global_root>/<package_name>`, and an existing destination package directory is refused wholesale rather than merged. The Library browser's export/import dialogs are native `.rflib` file dialogs; imports target the global user library, not a project-local library.
- `draw_ui()` and `drawExtensionsPanel()` both dispatch through `externalToolActions()`; the Tools menu iterates `toolsMenuEntries()` (external tools the trust gate allows) and renders only actions whose `location == "tools"`, while the Extensions panel shows every declared action (or a single fallback Run button) once the tool is trusted. Both views disambiguate the ImGui item ID with the manifest id while passing the raw label to `runExternalTool()` — the Tools menu always adds the action index (`<label>##<id>-<i>`), the Extensions panel only where there are declared actions (`Run##<id>` for the no-menus fallback). Extension ids are deduplicated but labels are not, so a shared ID would let a click on one tool's row launch another's (issue #130)
- App-level integration tests may use `testExtensionManager()` and `testExtensionResultMessage()` with an ImGui/ImPlot/ImNodes fixture
- The Spectrum Analyzer plot fills the panel's remaining height above a `SpectrumAnalyzerWidget::kMinPlotHeight` floor and reserves the readout rows below it (including the marker block while enabled), so the panel can be resized without dead space; the `test_engine` layout regression reads the plot rect black-box via `ctx->ItemInfo("Spectrum")`
- `load_window_states()` runs on construction to restore persisted window visibility toggles
- Per-PFB IQ Plot / Channelizer Grid window visibility lives in `PFBViewManager::iqVisibility()`/`gridVisibility()` (indexed in lockstep with the manager's widgets, in registry order) and has no View-menu entry since instances are dynamic; closed windows are reopened via "Show IQ Plot"/"Show Channelizer Grid" checkboxes in the PFB properties panel, wired each frame through `InspectorPanel::setPFBWindowVisibility()` (stores the stable vector pointers, not element pointers, since `sync()` replaces the vectors on every component-set change)
- The PFB properties inspector reports the active channel's integrated noise power in dBm and its effective noise bandwidth in MHz; the engine derives both from the channel's response weights and current input frequency grid. This channel-level readout is distinct from the two Spectrum outputs (W/Hz) and their analyzer-RBW-integrated display.
- Inspector numeric drawers pass a local copy of the engine value to `utils::inputDouble()`/`utils::inputFrequency()` and write it back only when the helper reports a change, so viewing a component never edits it, even when a value lies outside the inspector's range (the field contract is in the root AGENTS.md). A drawer that feeds several fields into one setter (a generator tone row, band-pass/band-stop cutoffs) therefore passes every field the user did not edit through unchanged.
- The Network Analyzer panel is a singleton like the Spectrum Analyzer: `View > Network Analyzer` toggles `m_show_na`, which persists through `SessionState` (`WindowState`/`NetworkAnalyzer`) and drives `m_na_engine.update()` + `m_na_widget->draw(...)` each frame while visible
- Receiver Requirements is a separate `View > Receiver Requirements` singleton dockable view; visibility persists as `WindowState/ReceiverRequirements`, while the band and optional metric limits/conditions are project data persisted by `ProjectSerializer`. `RfSimulatorApp` updates the Network Analyzer exactly once per frame whenever either instrument view is visible, so Requirements-only visibility refreshes the shared Point A/B sweep. While Requirements is visible, the app obtains tone options only from the component at Point A (only generators expose choices), calls the app-owned receiver engine with applied requirements and analyzer sweep, then passes its partial/full output-power and IIP3 vectors plus current gain/NF vectors to the evaluator and widget. The engine advances at most 4 ms of scratch-stimulus work per visible frame; closing Requirements pauses it without discarding same-request progress, and reopening resumes it. A changed request signature resets pending work. The signature holds only measured inputs: Point A/B, the sweep grid, which metrics are enabled, the enabled metric's tone selector or IIP3 conditions, and the measured path's signature (every path component's state, including Point A's generator, and the links between them). Pass/fail limits, band edges, a disabled metric's conditions, and links off the measured path keep cached samples; the evaluator re-checks them against the retained samples each frame. A lone Point A tone may be preselected; multiple tones require explicit selection. A missing, stale, or frequency-ambiguous selector stays Incomplete with no fallback. Applied requirement/source-tone changes mark the project dirty. Outcomes are Not configured, Invalid configuration, Incomplete, Pass, or Fail; only complete valid configured requirements can Pass (green), Fail is red, and all other tones are neutral. Draft edits show neutral `Unapplied edits`, never a stale Pass/Fail.
- Network Analyzer and receiver measurements share `findMeasurementChainPath()`: every component on a forward path from Point A's component to Point B's component. `IsolatedChainRunner` clones the components after Point A's with their exact input/output ports and runs them in topological order, only in an app-provided scratch graph/registry; Point A's own component is never cloned because the stimulus replaces its output, and it must feed the circuit through a single output port (one port may feed several inputs; a 1:2 switch at Point A feeding both bank branches through its two ports is no-data, because the shared stimulus would ignore its throw). Point B selects the exact output port read. Branches may rejoin only at an `rf_switch_spdt_2to1`, so a switched filter bank keeps both branches under that engine's model (selected throw at insertion loss first, the other at isolation, tones concatenated). Combiners and other multi-input components (Point A's own component is exempt), two links into one input pin, cycles, and any input fed from outside the circuit (e.g. a second live source) are rejected as no-data. The instruments read the shared circuit differently: analyzer Gain (a relative transfer, dB) is the first tone at each sweep frequency — at a 2:1 switch the selected throw's, else the other throw's leakage if that throw carries one (a non-S-parameter `IdealFilter` drops out-of-passband tones), else no data; a first tone more than 100 dB below the stimulus is also no data, even with a stronger tone behind it — and NF_dB = 10*log10(P_noise,out / (G_linear*kT)) with G_linear from that Gain while P_noise,out includes both throws; receiver output power (absolute, dBm) and the IIP3 fundamental and IM3 lines sum every coincident tone as phase-aware phasors, so they also include the unselected throw's same-frequency leakage, which Gain omits wherever the selected throw carries a tone. How far the instruments then differ depends on both switches' settings, what each branch passes or generates at that frequency, and the tones' relative phase; the `[issue169]` tests pin concrete cases.
- The Power Meter panel is a singleton observer: `View > Power Meter` toggles `m_show_power_meter`, its window visibility persists through `SessionState` (`WindowState`/`PowerMeter`), and its selected output pin remains session-only and is cleared when project state is reset or loaded; measurement logic stays independent of ImGui
- The Filter Calculator window is toggled by `View > Filter Calculator` (`m_show_calculator`, persisted through `SessionState` `WindowState`/`FilterCalculator`); its design/metrics cache is rebuilt only after the control being dragged/typed releases (`IsAnyItemActive` gate), since a full resynthesis costs seconds at worst-case M=2048/K=64
- `CircuitRuntime` owns live component/graph/view lifetime, component IDs, topology validation and commands, synchronous input rewiring, and topological engine updates. `GraphEditorActions` is the only adapter that mutates probe/group/selection/part-number state and rebuilds derived group boundaries; `EditorCommands` is the only path user-level edits take to it and to the runtime's topology commands.
- `CircuitRuntime::epoch()` starts at zero, advances exactly once at the end of each `clearComponentsAndResetIds()` call, and does not change for ordinary component or link edits.
- `ProjectSerializer` remains app-bound: it routes component/link create/remove/reset and component-ID restoration through the runtime, and probes/groups/selection/part numbers/boundary refresh through editor actions. Node positions, PFB views, Network Analyzer state, and window flags remain app-owned. `EditorCommands::removeComponent()` rewires (in the runtime), syncs component-bound views, then rebuilds boundaries and advances the revision, all before returning.
- The app owns the node-hover adapter. For ordinary components it measures the first output with `SpectrumAnalyzerEngine::computeStrongestToneSNRdB()` at the analyzer's current RBW. For a PFB, first output means the active channel, and SNR uses the strongest active-channel tone against that channel's integrated noise power; changing analyzer RBW does not affect that PFB SNR. The widget only renders the optional value returned by the callback.
- `TestFlowWidget::run()` wraps the test-flow `RunFlow()` in an all-engine snapshot/restore boundary: it serializes every engine in `ComponentRegistry::all()` before execution, restores each snapshot independently afterwards (one failure cannot strand the rest), then runs the shared `rewireComponentInputs()` pass so each `node().inputs[]` pointer matches the untouched graph. When every restoration succeeds, a run is net-neutral — every component's `serialize()` state, every graph link, and the project revision (hence the dirty flag) are exactly what they were before — and the widget never calls `markDirty()`. A restore that throws is the exception: the component whose `deserialize(snapshot)` failed may be left at its swept state, the failure is latched and reported, the run's result is suppressed, and the circuit must be reloaded (via `resetAfterCircuitReload()`) before another flow may run, since the live circuit may no longer match the project. `run()` is true only when execution completes without a fatal `FlowResult` error and every restoration succeeded; an individual measurement is not part of that condition — an invalid `MetricSample` (`valid == false`) is a normal result, preserved and rendered as `N/A` (JSON `null`), and never fails the run.
- `TestFlowWidget::preview()` never forms its own opinion of a flow: its `issues` are `ValidateFlow()`'s verdicts — the harness pass `RunFlow()` itself runs, exhaustive over every condition value and cheap enough to repeat each frame because it resolves each path once — plus one issue for a sweep over `kMaxRunRows`. `runnable` is `issues.empty() && !restoreFailed()`, so Run cannot be enabled for a flow `RunFlow()` would refuse; a condition `path` is a `serialize()` key rather than an inspector label, which makes a mistyped one — or a value the slot cannot take — the mistake this catches before the click. The per-entry `resolved`/`port_resolved` flags only colour the preview tables.
- `TestFlowWidget::run()` refuses a sweep above `kMaxRunRows` (10000) *before* snapshotting anything: `RunFlow()` executes the cartesian product synchronously on the UI thread (10 000 rows measured 4 s on a two-node circuit in an unoptimized build), so an unbounded flow is a frozen window rather than a long wait, and `preview()` reports the same limit so the disabled button always has a visible reason. The results table is height-bounded to `kResultTableRows` (with `ImGuiListClipper` over it): an unbounded table put all 10 000 rows inside the visible area, where ImGui clips nothing, and measured 34 ms per frame against 0.27 ms bounded.
- A failed restoration latches `restoreFailed()`: the run reports failure and later runs are refused until `resetAfterCircuitReload()` clears the latch and the stale result. `RfSimulatorApp` calls that reset from `newProject()`, after a *successful* `loadProject()`, and after a *failed* `loadProject()` that reported `lastLoadReset()` — every load that replaced the circuit with empty state is a reload, while a failure that leaves the live circuit intact keeps the latch, its notice, and the result; the retained flow selection is revalidated against the replacing circuit by `preview()` on demand, which resolves flow component ids by iterating `ComponentRegistry::all()` and matching `IComponentEngine::id()` — never `ComponentRegistry::find()`, which is keyed by graph-node id.
- `TestFlowWidget` authors flows too (issue #155), into an in-tool *draft*: `spec()` is the single accessor `preview()`, `run()` and `saveFlow()` read — the draft while one exists, otherwise the loaded file's spec — so the panel can never validate one flow and run another. Every load clears the draft (the file is the truth again) and the status says it was discarded; `newFlowFromCircuit()` says the same when it replaces one; `resetAfterCircuitReload()` keeps the draft because `preview()` revalidates it against the replacement circuit on demand. `draftActive()` is that "unsaved edits exist" signal, and a *refused* edit never creates a draft: every refusal is checked before the draft is materialised.
- Every reference the authoring form offers is read from the live circuit — component ids from `ComponentRegistry::all()` matched on `IComponentEngine::id()`, keys from `describeConditionPaths()` over that engine's own `serialize()` — so an invented component or a non-existent key cannot be authored at all, and `authoringComponents()` marks the keys the draft already sweeps. `newFlowFromCircuit()` supplies only what a flow cannot do without (a measurement on the first component with an output port, port 0, `power_dBm`) and pre-fills the form with the first sweepable key and its *current* value; the sweep itself is the author's Add condition click.
- `addCondition()`/`updateCondition()`/`addMeasurement()` validate their candidate through `ValidateFlow()` and report its wording, so a refusal at the form is the verdict Run would give later (a fractional value for an integer slot is refused at the edit, not mid-run), and they enforce the loader's `DuplicateConditionTarget`/`DuplicateMeasurement` rules that `ValidateFlow()` does not check — a draft the panel runs must also be a file that loads back. A refused edit leaves the draft untouched, and creates none.
- `saveFlow()` refuses, with a status, a flow with no measurement or one `ValidateFlow()` rejects, then writes the document with `buildFlowDocument()`/`writeFlowFile()` and loads it straight back, so the panel holds exactly the file's contents (the loader having verified them). `reloadFlow()` re-reads the selected path — a hand edit is picked up without re-picking the file — and clears the draft. Native dialogs stay the app's: `openTestFlowDialog()`/`exportTestFlowDialog()`/`saveTestFlowDialog()`, handed to `draw()` as callbacks (the save one optional).
- The Authoring section renders the component/key/values and component/port/metric forms (a non-numeric key is listed but disabled, with its JSON type as the reason) plus per-row Edit/Remove in the preview tables. A condition whose `path` does not resolve is marked red and answered with `path_hints` — up to `kMaxPathHints` sweepable keys from that engine — because a mistyped `serialize()` key (never an inspector label) is the likeliest authoring mistake. The values field's ImGui buffer is grown from the model text (`kValuesBufferHeadroom` past its end) instead of a fixed size: a fixed buffer truncated a long sweep's text on the next keystroke and stored the truncation back, which would have dropped values from a list the harness then runs as complete.
- Test-flow selection, load state, and the last result are session-only and never persisted; `View > Test Flow` toggles `m_show_test_flow`, which persists through `SessionState` (`WindowState`/`TestFlow`) exactly like the other panel toggles
- Destructor saves window state via `SessionState`
