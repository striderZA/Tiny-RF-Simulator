# Tests - AGENTS.md

## Purpose

Own the Catch2 v3.4.0 unit test suite and ImGui test engine UI tests. Verify all DSP engines, node graph operations, touchstone parser, and application components produce correct results. Prevent regressions across the modular build.

## Local Contracts

- All tests use Catch2 v3 `TEST_CASE` / `SECTION` macros
- Floating-point comparisons use `Catch::Approx` from `<catch2/catch_approx.hpp>`
- Benchmark cases use `Catch::Benchmark::BENCHMARK` from `<catch2/benchmark/catch_benchmark_all.hpp>`
- Test files are named `test_<component>.cpp` matching the module name
- Build via `cmake --build build && ctest --test-dir build` or direct `build/bin/tests`
- App and serializer fixtures inspect live circuits through const `testGraphEngine()` / `testComponents()` views and set up topology/editor state through explicit app test commands; do not mutate the live graph or registry directly. Those commands forward to the editor's `EditorCommands`, so fixture setup is a real project edit that advances the revision and dirties the project (except probe add/remove, which keep their pre-existing no-revision semantics): to prove an operation recorded no edit, compare `projectRevision()` before and after (non-vacuous even from a dirty baseline) rather than asserting a clean `isDirty()`.
- App/serializer integration cases construct `RfSimulatorApp` only inside `ImGuiFixture` with ImGui, ImPlot, and ImNodes contexts.
- Adding a new test file? Register it in `tests/CMakeLists.txt` via `add_standalone_test(test_<name> SOURCES test_<name>.cpp LIBS ...)` (the standard helper; preferred for new coverage — see the MinGW ceiling below). Add to the main `tests` binary's `TEST_SOURCES` only for a pure extension of an existing component already compiled into it.
- `test_agent_api` stays app/UI-free: its `ApiFixture` uses `CircuitRuntime`, `EditorCommands`, analyzer engines, and a test `IAgentHost`; scratch clones must use `ComponentTypeRegistry`, never a handwritten engine factory.
- `test_receiver_requirements_project` exercises project persistence separately from the UI-free validation target: valid band/gain/NF/output-power/IIP3 limits and optional measurement conditions round-trip; legacy absence remains Not configured; malformed receiver fields including raw `1e400` restore unrelated components and project path while retaining Invalid configuration, which saves/reloads only through an explicit invalid marker and diagnostic. Overflow elsewhere is rejected, mixed with receiver overflow or not, and quoted part-number strings survive recovery. Supplied conditions are validated even when disabled, enabled IIP3 sweeps are bounded to 3–101 levels, and New clears all requirement state including optional conditions. Scratch files use `test_temp_paths::processTag()`. Since it constructs `RfSimulatorApp` inside `ImGuiFixture`, its CTest registration is `RUN_SERIAL TRUE` for shared `app.ini`.
- **MinGW-w64 test-registration ceiling:** this toolchain silently drops any `TEST_CASE` registered beyond the ~223 already linked into the main `tests` executable (verified 2026-08-09; the release.yml Windows jobs enforce the 223 floor with a `--list-tests` count guard). Do not add new `TEST_CASE`s to `test_main.cpp` or any file already compiled into the `tests` target — give the new coverage its own standalone executable instead (`add_executable(test_<name> test_<name>.cpp)` + `target_link_libraries` + `add_test`, following `test_attenuator`, `test_combiner`, `test_network_analyzer`, `test_component_authoring`, `test_tutorial_state`, `test_extensions`, `test_issue37_pfb_input_removal`, `test_issue70_pfb_reconnect`, `test_issue42_multi_output`, `test_component_dispatch`, `test_signal_domain`, `test_path_containment`, and `test_issue48_json_loader`), and run it directly (`build/bin/test_<name>.exe`) rather than relying on `ctest`. `test_issue48_json_loader` covers malformed project/library input via `TEST_CASE`s in its own standalone executable, outside the main `tests` registration ceiling, so it must be run directly (`build/bin/test_issue48_json_loader.exe`).
- Platform-specific tests (e.g., Windows-only session state) are gated with `#ifdef WIN32` in CMakeLists.txt
- The standalone `test_session_state_unicode` target is Windows-only, links `common`, and passes a unique Unicode temporary file path to `SessionState(std::filesystem::path)` so it never reads or mutates the executable-relative `app.ini`.
- **Scratch paths must be unique across processes, not just across calls.** `catch_discover_tests(tests)` registers one CTest entry per `TEST_CASE`, so under `ctest -jN` several cases run as separate processes at once and a `static` counter restarts at 0 in each of them. Resolve scratch paths under `temp_directory_path()` and tag each name with `test_temp_paths::processTag()` (`tests/test_temp_paths.h`), plus a counter where one process writes several files: the tag is what makes the name unique whichever way the case runs, while a relative name lands in the checkout for a standalone executable (`WORKING_DIRECTORY` is the source tree) or in `build/tests` for a main-binary entry. Converted to that form: `test_component_library`, `test_component_dispatch`, `test_issue116_collapsed_groups`, `test_issue70_pfb_reconnect` and `test_rf_switch_project`. A `random_device`-derived name is not a substitute: it is only *probabilistically* unique, and a collision clobbers the other process's file rather than failing loudly. The older fixed-name `<temp>/rfsim_ext_*` fixtures are safe only because exactly one `TEST_CASE` owns each name.
- **Exe-relative app state is shared by every test executable in `build/bin`.** `SessionState` derives `<exe_dir>/app.ini` from the running executable and `RfSimulatorApp::~RfSimulatorApp()` writes it, so every app-level test plus each `test_session_state.cpp` case read-modify-write that one file concurrently — unsolved, and the reason `-jN` is not unconditionally safe. `LayoutManager` derives `<exe_dir>/layouts` and `TutorialState` derives `<exe_dir>/.tutorial_completed` with the same sharing, so `test_ui` (`test_engine/CMakeLists.txt`) is `RUN_SERIAL TRUE`: it is the only test that drives all three through the app, while `tests/test_layout_manager.cpp` calls `remove_all(layoutsDir())` and `tests/test_tutorial_state.cpp` removes the marker, and without serialization another test deletes the file `test_ui` is asserting on (reproduced 2026-09-18 by deleting the file under the run: with `layouts/UITestLayout.ini` deleted, `layout_manage_delete_removes_file` fails the `exists()` check that opens it, and two concurrent `test_ui` processes hit that same failure on their own because they share the directory; with the tutorial marker deleted, the cases that assert it — `tutorial_completes_and_persists` and `tutorial_first_run_prompt_marks_completed` — fail, though that marker pairing was not reproduced by its natural `tests/test_tutorial_state.cpp` partner in 50 runs). CI never runs `test_ui` (`-E "Benchmark|test_ui"`), so this costs local `-jN` runs only. Concurrent `test_ui` invocations are unsafe in the same way: two at once fail 4/4, with `layout_manage_delete_removes_file` losing the shared `layouts/UITestLayout.ini` and the tutorial cases cascading off the resulting missing menu item.
- `test_network_analyzer` covers Network Analyzer stimulus/results and production app host/clone factory integration, plus `findMeasurementChainPath()` discovery and `IsolatedChainRunner` successive stimuli, exact ports, singly-fed switches, and switched filter banks (`[issue169]`: topological order with both branches wired, matched/flipped/mismatched throws and unselected-branch noise against the live engines, an `IdealFilter` bank whose Gain reads the other branch's leakage in the selected filter's stopband, the app clone factory); rejection of combiners, outside-fed merges, two links into one input, cycles, and a Point A component feeding the circuit through two outputs; `prepare()` refusing paths it cannot wire faithfully; and live-state isolation. It is `RUN_SERIAL TRUE` because app destruction writes shared exe-relative `app.ini`.
- **`test_test_flow_widget` is `RUN_SERIAL TRUE`** for the same shared-`app.ini` reason: it constructs a real `RfSimulatorApp` and drives the Test Flow panel, whose `View > Test Flow` visibility flag round-trips through the exe-relative `SessionState` file every other app-level test also read-modify-writes. Its `tests/CMakeLists.txt` `set_tests_properties(... RUN_SERIAL TRUE)` serializes only within one `ctest` invocation.
- **Tooltip coverage is split by what each harness can observe:** the `test_ui` engine sees tooltip *windows* only — ImGui registers text items with id 0, so it cannot query tooltip text — which is why `test_engine/ui_tests.cpp::hover_tooltips_node_link_subcircuit` asserts that a node body, a link, and a collapsed subcircuit block each raise an `ImGuiWindowFlags_Tooltip` window and that an empty-canvas point raises none, plus that the node-body callback data the app hands the widget is populated (non-empty summary, `snr_dB` set). `test_engine/ui_tests.cpp::spectrum_analyzer_out_of_range_bandwidth_tooltip_is_preserved` sets RBW/VBW below range, hovers each control, and asserts their range/help tooltips share one window without inspecting rendered text. The standalone targets assert the *data*, never a rendered string: `test_node_hover_snr` pins the `NodeHoverInfo` the widget callback returns (summary passthrough, first-output SNR, empty-optional fallback) and `test_spectrum_analyzer_snr` pins the measurement behind that number. The widget's node-hover text — the summary line and formatted `SNR: %.1f dB` / `SNR: --` row — is not independently asserted by any test (ImGui text items are unqueryable, and the adapter test stops at the callback value); it is covered by source review of `showNodeHoverTooltips()`. Do not add tooltip-text lookups to the UI test.
- **Tests that mutate the built-in extension root must be `RUN_SERIAL TRUE`.** `ExtensionManager` hardcodes `PROJECT_SOURCE_DIR/extensions` as its highest-precedence scan root and every scan enumerates it, so a test writing a manifest there (`test_issue45_extension_trust`, `test_extensions`) is visible to any concurrently running test that counts discovered tools (`test_extensions`). The root is not injectable, so the pair is serialized in `tests/CMakeLists.txt` rather than isolated. `RUN_SERIAL` serializes within one ctest invocation only — a second concurrent `ctest` against the same build tree can still overlap them (observed 2026-09-18) — and it cannot cover a plant left behind by an interrupted run, which fails the next `test_extensions` run with `2 == 1` even when that run is alone. The `ScopedRemove` helpers now report a failed removal through Catch2's bare `WARN(...)` macro (a macro, not a `Catch::` symbol) instead of swallowing the error.
- **Mid-sweep receiver assertions must cap the engine.** `ReceiverPerformanceMeasurementEngine::update()` spends a 4 ms wall-clock budget per call, so how far a sweep gets in N frames depends on build and machine speed: an optimized build finishes the 201-point, 101-level `test_ui` sweep inside one multi-frame menu click. A test that needs a sweep still running after some number of frames calls `setMaxRunsPerUpdate()` on `testReceiverPerformanceMeasurementEngine()` and restores `std::nullopt` on every exit path with an RAII guard, as `receiver_requirements_view_updates_analyzer_and_resumes_receiver_measurements` does.
